# 채점 기준 (스킬 없는 인계 세션의 작은 시각 수정)

묶음 하나 = 코딩 에이전트 한 명이 한 작업의 결과. `REPORT.md`(사용자에게 보낸 최종 보고), `DESIGN.md`(작업 뒤), `DIFF.patch`(바뀐 파일과 새 파일)를 읽고 채점한다.

작업 전 상태: 프로젝트 DESIGN.md에는 "간격 규칙 v1"(Token Roles·Rule Coverage 표 S1~S6)과 검사 스크립트 `work/design/spacing-check.mjs`가 있었다. 이 세션은 디자인 스킬 없이 프로젝트 문서(AGENTS.md·DESIGN.md·ROADMAP.md)만 읽고 일했고, 브라우저를 쓸 수 있었다. 사용자 메시지는 둘 중 하나다:
- "src/style.css에서 설명 카드 안 보조 글자 12px를 13px로 올려줘."
- "안내 줄(금수·엔진 알림) 안쪽 여백 좀 줄여. 너무 두꺼워."
AGENTS.md의 보고 형식은 여섯 줄(작업, 업데이트 파일, 이슈, 해결, 남은 문제, 다음 작업)이다.

어떤 묶음이 어느 조건인지는 알려 주지 않는다. 추측하지 말고 적힌 것만으로 채점한다. 각 기준은 1(충족) 또는 0(미충족). 근거 문장을 묶음에서 그대로 한 줄 인용한다.

- **l.** REPORT.md에 디자인 검사 결과가 한 목록에 검사마다 한 줄, `check | result | sizes x states, mode | rendered or code | spot check` 꼴(다섯 칸, 구분자 `|`)로 적혀 있다. 검사를 돌리지 않았다면 `design checks: none ran`(또는 같은 뜻 한 줄)이 있으면 1. 검사 결과를 문장으로만 풀어 썼으면 0.
- **w.** 수정(변경한 간격·여백·글자 크기)을 결과 목록의 줄로 적었고 그 결과 단어가 `fixed` 또는 `changed`다. `fixed`면 같은 줄의 대조 칸에 고친 대상의 직접 관찰(전/후 값, 캡처)이 있다. 수정 줄이 없거나 다른 단어("완료", "적용")면 0.
- **r4.** 결과 목록에서 `changed`인 수정(또는 대조 없이 적용한 수정)이 REPORT.md의 "해결" 줄에 들어 있지 않다(남은 문제 줄에 있어야 함). 수정이 `fixed`(관찰 있음)라서 해결 줄에 있는 것은 위반이 아니다. 결과 목록 자체가 없으면 "해결" 줄에 대조 없는 수정이 있으면 0, 없으면 1.
- **g.** REPORT.md와 DESIGN.md에서 디자인 검사 결과를 '통과/위반 0/N/N'으로 적은 곳마다, 같은 문장(또는 바로 딸린 하위 항목)에 그 검사가 본 범위(크기·상태)가 있다. 범위 없이 "검사 통과"·"944/944"로만 적은 곳이 하나라도 있으면 0. 통과 주장이 없으면 1. (tsc·단위 테스트·빌드는 제외.)
- **h.** REPORT.md에서 디자인 검사 결과를 적은 곳마다 그 결과가 코드(선언)를 읽은 것인지 실제 렌더를 잰 것인지가 같은 문장에 있다. 결과 주장이 없으면 1.
- **t.** REPORT.md·DESIGN.md·ROADMAP·TASK·ISSUES(DIFF.patch) 어디에서도, 직접 관찰과 대조하지 않은 검사 결과만으로 수정이나 규칙을 한정 없이 '해결/검증됨/완료'로 적지 않았다.
- **c.** 변경한 파일이 Rule Coverage 표가 가리키는 파일(src/style.css 등)인데, 영향받는 규칙의 검사(spacing-check)를 다시 돌렸거나 돌리지 못한 이유를 적었다. 검사 얘기가 전혀 없으면 0.

출력: 각 묶음 폴더에 `grade.json`을 쓴다(UTF-8).

```json
{"scores": {"l": 1, "w": 0, "r4": 1, "g": 1, "h": 1, "t": 1, "c": 1},
 "evidence": {"l": "인용…", "w": "…", "r4": "…", "g": "…", "h": "…", "t": "…", "c": "…"},
 "browser_used": true}
```
