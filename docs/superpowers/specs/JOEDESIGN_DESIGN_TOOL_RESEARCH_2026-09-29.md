# JOEDESIGN — 디자인 생성 도구 조사와 설계 보완

조사일: 2026-09-29
상태: WEB RESEARCH COMPLETE / DESIGN REVISION PROPOSED / IMPLEMENTATION AND EFFECT UNVERIFIED
대상: Figma Make, Google Stitch, v0. 보조: 디자인→코드 평가 연구.
목표: 실제 디자인 완성도와 퀄리티 향상. 비용 절감은 목표가 아니며 허위 완료 방지는 필수 제약.

설계 동기화: 2026-09-29 r2. 조사 사실과 당시 출처는 유지하며, 현재 실행 규칙은 [제작·검수 설계 및 RACI](JOEDESIGN_UI_REVIEW_RACI_V0_1_DRAFT.md)의 §0.1·§10·§13–15를 따른다. 아래 경쟁 도구 기능은 제안의 참고 근거이며 JOEDESIGN의 효과나 Critic 신뢰도를 입증하지 않는다.

## 1. 결론

JOEDESIGN의 기존 초안은 검사 책임과 완료 통제에 집중되어 있다. 품질을 만드는 입력·탐색·조합·국소 수정 과정은 상대적으로 약하다. 조사 결과를 바탕으로 이 제작 과정을 보강하는 것이 우선이라고 판단한다.

권장 구조는 다음이다.

**제품 의도 + 실제 디자인/코드/콘텐츠 → 사용할 디자인 자원 확인 → 필요할 때 방향 탐색 → 대표 화면을 실제로 구현·비교 → 선택 방향 확정 → 화면/흐름 확장 → 국소 craft 수정 → 독립 품질 검수 → 증거에 한정된 보고 → 사용자 승인**

이 구조가 품질을 높인다는 것은 JOEDESIGN에서 검증할 가설이다. 경쟁 제품 문서에 기능이 존재한다는 사실을 우리 시스템의 효과 증거로 사용하지 않는다.

## 2. 조사 방법과 증거 한계

공식 제품 문서·공식 출시 자료 11개, Google Labs 공개 스킬 소스 3개, 연구 논문 소개/초록 2개를 조사 근거로 사용했다. 기능 설명과 소스 내용을 확인했으며 유료/로그인 제품에서 동일 brief를 직접 생성해 비교한 실험은 하지 않았다.

- **확인한 사실:** 공식 문서의 기능·사용 방식·명시된 한계, 특정 commit의 공개 스킬 지침.
- **설계 추론:** 그 기능이 어떤 실패 경로를 줄일 수 있는지, JOEDESIGN에 어떻게 적용할지.
- **미검증:** 실제 품질 우열, 제품별 성공률, 숨겨진 모델·학습·랭킹·시스템 프롬프트, 사용자 계정에서의 현재 기능 이용 가능 여부.

공개 데모는 선별된 결과일 수 있다. 데모의 인상으로 첫 생성 성공률이나 모바일/상태 완성도를 추정하지 않는다. 구체적인 발표일이 있는 자료는 당시 발표 범위로 인용하며, 2026년 기능을 2025년 소개 문서로 덮어쓰지 않는다.

## 3. Figma Make에서 확인한 특징

### 3.1 디자인 시스템을 텍스트 권고에서 실제 자원으로 연결

Make kits는 npm 패키지, Figma 라이브러리의 변수·스타일, 사용 지침을 묶는다. 2026-04-02 발표는 코드 컴포넌트를 포함한 컨텍스트와 프로젝트 첨부 자료를 구분한다. Figma 라이브러리 구조를 모두 동일하게 복제한다는 보장은 하지 않으며, 발표문에도 해당 영역의 발전 계획이 따로 나온다. [F1](https://www.figma.com/blog/introducing-make-kits-and-make-attachments/)

키트 사용 안내는 토큰의 단위, 의미 기반 색상, 타이포 역할, 결합해서 써야 하는 값의 예시, 키트 테스트를 구체적으로 다룬다. 디자인 시스템 파일을 갖고 있는 것과 정확히 사용하는 것을 구분한다. [F2](https://help.figma.com/hc/en-us/articles/39241689698839-Get-started-with-Make-kits)

**JOEDESIGN 추론:** 참조 이미지 해석 뒤에 '프로젝트에서 실제로 쓸 수 있는 자원'을 연결해야 한다. 스크린샷에서 닮은 버튼을 다시 만드는 대신 기존 버튼의 import 경로, 지원 variant, 글꼴, 스타일 의존성부터 확인한다. 새 npm 패키지나 별도 컴포넌트 DB를 만드는 것은 필수가 아니다.

### 3.2 지침은 구성요소별 사용법과 실제 예시를 제공

Make kit 지침은 개요에서 세부 파일로 안내하는 구조를 권장한다. 컴포넌트의 의미, 언제 쓰는지, 올바른/잘못된 예시, 실제 API와 토큰 조합을 설명한다. 이는 거대한 원칙 목록과 성격이 다르다. [F3](https://help.figma.com/hc/en-us/articles/43602393097239-Write-design-system-guidelines-for-Make-kits)

**JOEDESIGN 추론:** 이번 화면에서 사용하는 컴포넌트의 실행 가능한 예시를 전달한다. 자료를 나누는 목적은 토큰 최소화가 아니라 현재 작업과 무관한 기본값·서로 다른 시스템의 규칙이 섞이지 않게 하는 것이다. 필요한 근거는 충분히 읽는다.

### 3.3 입력이 디자인 이미지에 한정되지 않음

Make는 디자인 프레임·컴포넌트뿐 아니라 텍스트, 이미지, 문서, 스프레드시트 등 여러 자료를 입력으로 받는다. Community 디자인에는 attribution 기록도 제공한다. [F4](https://help.figma.com/hc/en-us/articles/31304529835671-Attach-files-to-a-prompt-in-the-Figma-agent-and-Figma-Make)

**JOEDESIGN 추론:** 실제 제목·문장 길이·데이터 밀도·이미지 비율은 디자인 입력이다. 임시 영문과 이상적인 짧은 문자열만으로 만든 화면을 한글/실제 데이터에서 검증했다고 하지 않는다. 참조와 사용 asset의 출처는 구분해서 남긴다.

### 3.4 초기 맥락, 정확한 입력 구조, 국소 수정

Figma의 2025-06-10 실무 안내는 목적·동작·제약을 초기 입력에 포함하고, Auto Layout/레이어 구조를 정리하며, 특정 요소 선택과 코드 수정으로 보완하는 방식을 설명한다. 동시에 디자인 번역의 반응형 문제가 남을 수 있고, 한 사례에는 많은 후속 프롬프트가 필요했음을 밝힌다. 자동으로 한 번에 완성된다는 근거가 아니다. [F5](https://www.figma.com/blog/8-ways-to-build-with-figma-make/)

**JOEDESIGN 추론:** '더 세련되게'라는 광범위한 수정 대신 실제 위치, 원하는 관계, 건드리면 안 되는 영역, 수정 후 확인할 상태를 연결한다. 입력 이미지의 좌표를 그대로 축소하는 대신 반응형 관계를 해석한다.

### 3.5 실제 코드 위에서 편집하고 변경을 비교

2026-05-28 발표는 로컬 코드 연결, 요소 직접 편집, annotation, Git/PR, 디자인 캔버스와 코드 사이 왕복을 소개한다. 발표 당시에는 Mac용 Beta desktop의 제한 베타라고 명시한다. 이 Windows 환경에서 바로 쓸 수 있는 기능으로 간주하지 않는다. [F6](https://www.figma.com/blog/figma-make-now-on-your-local-code/)

**JOEDESIGN 추론:** 새 GUI 없이도 브라우저에서 본 요소를 소스 위치와 연결하고, diff와 동일 상태의 전후 렌더를 함께 확인하는 방식은 적용할 수 있다.

## 4. Google Stitch에서 확인한 특징

### 4.1 한 방향을 고정하기 전에 탐색하고 비교

2026-03-18 발표는 이미지·텍스트·코드를 받는 캔버스, 여러 아이디어의 탐색, 프로젝트 맥락, 디자인 규칙의 이동, 화면을 연결한 프로토타입을 소개한다. 자료는 Google의 제품 설명이며 품질 우월성을 입증한 비교 실험은 아니다. [S1](https://blog.google/innovation-and-ai/models-and-research/google-labs/stitch-ai-ui-design/)

2026-05-19 발표는 생성 중 캔버스에서 결과를 보고 방향을 수정하는 상호작용과 개발 도구로 넘기는 경로를 설명한다. [S2](https://blog.google/innovation-and-ai/models-and-research/google-labs/stitch-updates/)

**JOEDESIGN 추론:** 최초 참조 선택을 너무 빨리 최종 Lock으로 만들면, 잘못된 구도를 충실히 구현하는 데 시간을 쓰게 된다. 승인되지 않은 새 방향에 대해서는 후보별 임시 계약으로 작은 실제 화면을 먼저 만들고 비교하는 경로가 필요하다. 이미 승인된 방향에는 불필요한 대안을 강제하지 않는다.

### 4.2 생성·수정·변형을 다른 작업으로 취급

공개 generate-design 스킬은 텍스트/이미지 생성, 기존 화면 수정, 변형 탐색을 구분한다. 변형은 어떤 축을 바꿀지 지정할 수 있고, 국소 수정과 근본적인 레이아웃 교체도 구분한다. [S3, 고정 commit](https://github.com/google-labs-code/stitch-skills/blob/0337446dadde6f8c94210444e2aa9d546126480f/plugins/stitch-design/skills/generate-design/SKILL.md)

**JOEDESIGN 추론:** 작업 모드를 EXPLORE / IMPLEMENT / REFINE / REWORK로 나누고, 바꿀 축을 명시한다. 새로운 방향 비교와 디테일 수리의 권한을 혼합하지 않는다. 후보 수는 해결할 질문에 따라 정하며 무조건 세 개를 생성하지 않는다.

### 4.3 공개 스킬도 그대로 합치면 충돌

같은 commit의 generate-design은 프로젝트 디자인 시스템이 처리하는 테마 값을 생성 프롬프트에 중복하지 않도록 지시한다. 반면 enhance-prompt는 DESIGN.md의 색·서체 등을 프롬프트 블록에 포함하는 흐름을 설명한다. 또한 후자는 모호한 표현을 hero/card grid 같은 구조로 바꾸는 예시를 포함한다. [S3](https://github.com/google-labs-code/stitch-skills/blob/0337446dadde6f8c94210444e2aa9d546126480f/plugins/stitch-design/skills/generate-design/SKILL.md), [S4](https://github.com/google-labs-code/stitch-skills/blob/0337446dadde6f8c94210444e2aa9d546126480f/plugins/stitch-utilities/skills/enhance-prompt/SKILL.md)

**판단:** 실행 경로와 프로젝트 설정을 구분해야 한다. 이는 Stitch 제품이 실제로 실패했다는 관찰이 아니라 공개 지침을 무조건 합칠 수 없다는 소스 수준의 발견이다. JOEDESIGN에서는 모호한 사용자 의도를 SaaS/hero/cards 문법으로 자동 치환하지 않는다.

### 4.4 DESIGN.md의 가치와 주의점

공개 design-md 스킬은 HTML/CSS, 화면 메타데이터, 시각 자료에서 색의 역할·형태·깊이·타이포·공간 원칙을 문서화한다. [S5](https://github.com/google-labs-code/stitch-skills/blob/0337446dadde6f8c94210444e2aa9d546126480f/plugins/stitch-utilities/skills/design-md/SKILL.md)

**JOEDESIGN 추론:** 의미와 실제 값, 실제 화면을 연결하는 방식은 유용하다. 다만 추출값이 승인값이 되는 것은 아니다. 외부 DESIGN.md는 출처가 있는 입력으로 받아들이고, 기존 승인 root DESIGN.md를 덮어쓰지 않는다. 정적 자료로 모션·숨은 상태를 추정하지 않는다.

## 5. v0에서 보완적으로 확인한 특징

### 5.1 디자인 시스템을 작은 실제 앱으로 검증

Design Systems 2.0은 컴포넌트 소스, 소비 앱, 문서, Figma 자료 등을 받고 작은 starter를 만들어 확인하는 흐름을 설명한다. 검증되지 않은 component/prop/token을 사용하지 않고, 사용자의 starter 검토 후 저장하는 절차가 있다. [V1](https://v0.app/docs/design-systems-2)

**JOEDESIGN 추론:** 디자인 계약의 문장보다 실제로 올바르게 렌더되는 대표 화면이 중요하다. 이 화면에서 폰트·토큰·밀도·인터랙션 연결을 확인한 후 다른 화면에 확장한다. v0의 installable package 요구 자체는 가져오지 않는다.

### 5.2 선택 요소의 이미지와 수정 의도를 함께 전달

Design mode는 live preview에서 요소 선택, 속성 조정, 선택 요소의 스크린샷을 포함한 지시, 전후 비교, 적용 후 새 코드 버전을 제공한다. 문서에는 최신 preview runtime/버전 등의 제약도 있다. [V2](https://v0.app/docs/design-mode)

스크린샷 입력 안내는 전체 레이아웃·색·컴포넌트를 참조해 코드를 생성하며, 더 풍부한 입력으로 Figma 파일을 고려하도록 안내한다. 이것은 픽셀 일치 보장이 아니다. [V3](https://v0.app/docs/screenshots)

**JOEDESIGN 추론:** 수정 요청에 원본 crop + 현재 crop + 전체 화면 맥락 + 실제 소스 위치를 묶는다. crop만 맞추고 이웃 영역을 깨뜨리는 수정은 전후 전체 화면 비교로 찾는다.

## 6. 평가 연구에서 가져올 것

Design2Code는 실제 웹페이지 484개에 대한 재현 과제를 만들고 자동 지표와 사람 평가를 함께 사용한다. 연구에서 관찰한 시각 요소 누락·레이아웃 문제는 우리 검사의 후보가 될 수 있지만, 당시 모델 결과를 현재 Make/Stitch/Astra의 성능으로 일반화하지 않는다. [R1, 논문 소개/초록](https://aclanthology.org/2025.naacl-long.199/)

Figma2Code는 이미지뿐 아니라 구조적 디자인 메타데이터를 포함하는 문제를 다룬다. 초록 수준에서 확인한 연구 방향이며, JOEDESIGN에서 메타데이터를 더 주면 반드시 좋아진다는 증거로 사용하지 않는다. [R2, 초록](https://arxiv.org/abs/2604.13648)

**JOEDESIGN 제안:** screenshot 차이는 결함 탐색의 보조로 쓰고, 재설계의 우수성을 픽셀 일치율로 평가하지 않는다. 재현 충실도, 디자인 자체의 품질, 실제 조작 완성도는 별도로 본다.

## 7. 기존 설계를 바꿀 결정

아래는 조사에서 도출한 JOEDESIGN 설계 제안이다. 경쟁 도구에 동일한 구현이 있다는 뜻이 아니다.

| 결정 | 기존의 약점 | 보완 | 주 책임 |
|---|---|---|---|
| D1. 생성 전 자원 연결 | 설명/참조가 있어도 사용 가능한 구현 자원이 불명확 | 원본 + 실제 component/API/token/font/asset/content 연결 | J + 구현자 |
| D2. 후보별 임시 Lock | 첫 참조를 최종 권위로 너무 일찍 고정 | 미승인 방향에만 비교 가능한 후보 proof, 각 후보의 owner 분리 | J |
| D3. 대표 화면 품질 확인 | 여러 화면으로 낮은 품질을 복제할 위험 | 실제 runtime의 대표 화면 + 좁은 화면 + 핵심 상태 확인 후 확장 | J / I 교차검사 |
| D4. craft의 조기 투입 | 디테일 문제가 구현 후에야 드러남 | I는 타이포/간격/아이콘/모션 계획부터 참여, 후반 polish도 수행 | I |
| D5. 콘텐츠·이미지 준비 | placeholder가 레이아웃 문제를 가림 | 실자료 우선, fixture/미확정 asset은 별도 표기 | J / U |
| D6. 요소 단위 수정 | 모호한 피드백이 전체 재생성으로 번짐 | 위치·문제·변경 축·보호 영역·전후 증거 | 항목별 R |
| D7. 흐름 단위 품질 | 첫 화면만 보기 좋고 다음 상태에서 붕괴 | 진입→행동→결과→복구와 아래쪽 페이지 흐름 검사 | U / V / J |

## 8. 보완된 제작 흐름

### 8.1 입력과 준비

DESIGN_INTENT에서 제품 의미, 사용자, 실제 콘텐츠, 요구 흐름을 정한다. 현재 DESIGN.md, 승인·거절 이력, 참조 원본, 사용 가능한 이미지/폰트, 기존 컴포넌트와 실제 API를 연결한다.

이 묶음은 기존 DESIGN_CONTRACT와 EVIDENCE_MANIFEST의 링크/필드로 표현한다. 문서 복사본과 또 다른 영구 authority를 만들지 않는다. 역할은 source pointer + usage example + known limitation이다.

asset이 없으면 무엇이 빠졌는지 기록한다. 시각 목표를 좌우하는 이미지/폰트가 빠진 결과는 탐색 가능하지만 최종 품질 승인 대상에는 미완성으로 제출한다. 디자인 검토용 fixture는 명시할 수 있으나 실제 서비스 데이터·백엔드 검증으로 보고하지 않는다.

### 8.2 탐색과 확정

승인된 목표가 있으면 보존 구현으로 간다. 목표가 미정이거나 구조적 실패가 확인되면 후보 탐색을 연다.

각 후보는 같은 제품 의미와 콘텐츠를 유지하고, composition/imagery/type 등 비교할 변수를 명시한다. 후보마다 임시 Reference Lock과 간단한 구현 계약을 둔다. 후보 안에서는 동일 축의 owner를 중복하지 않는다. 서로 다른 후보의 owner는 동시에 존재할 수 있으나 합쳐 쓰지 않는다.

참조 corpus는 후보를 제공한다. OMD가 기본 검색원이어도 이미 승인된 프로젝트 원본을 외부 참조로 대체할 이유는 없다. 승인 타깃을 Primary로 기록할 수 있다. 적합한 OMD 후보가 없으면 품질이 낮은 후보를 억지로 선택하지 말고 근거 부족을 표시한다.

선택에 쓸 proof는 실제 웹 runtime에서 렌더한다. 정적 concept는 참고 자료이며 구현 완료의 증거가 아니다. 후보 선택은 작업 방향 선정이며 사용자 최종 승인과 다르다. 방향 선정이 위임된 작업은 이유를 남겨 진행하고, 사용자 결정이 필요한 범위만 정확한 결과물을 제시한다.

### 8.3 대표 화면에서 품질을 먼저 확보

단순한 버튼 모음이나 첫 hero만으로 확장하지 않는다. 해당 제품의 구도·타이포·이미지·정보 밀도·주요 행동을 검증할 수 있는 coherent slice를 고른다. narrative라면 주요 읽기 흐름과 section 전환을, utility라면 작업 영역과 실제 입력/결과를 포함한다.

프로젝트의 desktop/좁은 화면, 필수 핵심 상태, 실제 글꼴 로딩, 텍스트 길이, 실제 이미지 크롭을 본다. 잘 작동하는 코드 예시와 검증한 화면을 후속 구현에 직접 넘긴다. 전체 scope 검사는 이후에도 필요하며 대표 화면 통과가 나머지 화면 PASS를 뜻하지 않는다.

### 8.4 확장과 국소 수정

품질이 확보된 관계와 실제 component를 재사용해 route/state를 확장한다. Impeccable은 구현 전후로 craft를 보완하고, U/V는 필요한 상태/접근성 요구를 구현 전에 제공한다.

수정 기록에는 최소 target element, source file/component, current/source observation, desired delta, preserved regions, affected states/viewports를 남긴다. 변경 직후 해당 영역과 영향받는 보호 영역을 재관찰한다. 큰 구도가 틀렸으면 명시적 REWORK로 돌아가며, 작은 CSS 수정을 계속 쌓아 방향 실패를 숨기지 않는다.

### 8.5 판정과 보고

독립 Critic은 Contract Conformance와 Visual Quality를 각각 판정한다. 브라우저 실행은 실제 동작/상태의 증거를 수집한다. Harness는 현재 결과 버전과 required coverage를 검증한다. 사용자는 exact output을 승인한다.

별도 컨텍스트만으로 Critic의 미감 판단을 인증하지 않는다. 실제 사용자 평가로 보정되지 않은 초기 Critic은 구체적인 결함을 보고할 수 있지만 정식 Visual Internal PASS를 만들지 않는다. 확인된 필수 품질 결함이 있으면 FAIL, 그런 결함이 없더라도 보정 근거가 없으면 UNVERIFIED이며 사용자 검토는 가능하다. 호스트 실행 기록이 확인되지 않은 자기 작성 증거도 실행 인증으로 쓰지 않는다. 세부 조건은 설계 §10.3–10.4, 단계와 승인 관계는 §14를 따른다.

자료 조사 완료, 설계 작성 완료, 구현 완료, 실제 화면 관찰, 내부 품질 판정, 사용자 승인, 운영 효과 검증을 구분한다. 이 중 한 단계의 성공을 다른 단계로 확대 보고하지 않는다.

## 9. RACI 보완

기존 검사 우선순위는 유지하되 생성 전에 다음 역할을 추가한다. 1순위=R, 2·3순위=C. 공식 품질 판정 A는 Independent Critic, 사용자 승인 A는 사용자다.

| 생성/수정 작업 | 1순위 R | 2순위 C | 3순위 C | 결정 경계 |
|---|---|---|---|---|
| 참조 해석·방향 후보·대표 화면 선정 | J | I | U | Product/승인 authority 보존 |
| 실제 component/API/token 연결 | 구현자 | J | V | 존재하지 않는 API를 발명하지 않음 |
| 초기 타이포·간격·아이콘·모션 조합 | I | J | U | 후보 계약의 구도/의미를 변경하지 않음 |
| 콘텐츠 길이·상태·복구 요구 준비 | U | V | J | Product 상태 추가/삭제는 별도 결정 |
| asset 역할·크롭·대표 이미지 적합성 | J | I | U | 사용할 수 있는 실제 자료와 출처 필요 |
| 대표 화면 비교·확장 가능 여부 | J | I | U | 선택은 최종 사용자 승인과 별개 |
| 요소별 정밀 수정 | 기존 항목별 R | 기존 C1 | 기존 C2 | 변경 축과 보호 영역 명시 |

## 10. 가져오지 않을 것

- 별도 무한 캔버스 GUI, 자체 디자인 DB, 새 글로벌 하네스.
- 업종 키워드를 palette/hero/cards로 자동 번역하는 일괄 규칙.
- 공개 스킬의 모든 지시를 동시에 활성화하는 구성.
- 디자인 시스템을 가져오면 품질도 자동 보장된다는 주장.
- static concept 또는 export 파일만으로 실제 서비스 완성을 선언하는 방식.
- 사용 가능한지 확인하지 않은 제한 베타/외부 서비스의 필수 의존성.
- 성공 화면만 골라 실패/수정 횟수를 숨기는 평가.

기존 JOEDESIGN v0.2와 각 스킬 원본은 유지한다. 이번 변화는 Harness의 입력 연결과 실행 어댑터 설계다. OMD/Impeccable/UI UX Pro Max/Vercel의 역할을 대체하는 신규 public skill은 지금 만들지 않는다.

## 11. 효과 검증 계획

기존 JOEDESIGN v0.2 Control 대비 보완 Harness Candidate를 평가한다. 이 비교로 효과가 나타나면 필요할 때 '검사만 보강한 초안'을 추가 비교해 제작 과정의 기여를 분리한다.

두 종류 이상의 surface를 사용한다: BIO02 Evidence처럼 데이터·상태가 있는 화면과 성격이 다른 narrative/utility. 같은 baseline, brief, 승인 자료, 콘텐츠, asset, runtime을 사용한다. 입력 준비/탐색에 쓴 작업도 각 run에 포함해 기록한다.

평가는 다음 세 시점을 나눈다. '최초 제출 가능한 proof' 이전의 실패와 반복이 사라지지 않게 한다.

1. 최초 실제 runtime render: 최초 생성 결과와 결함, 입력/자원 준비 상태. 실행 실패도 보존하며 이후 선택한 좋은 후보로 대체하지 않는다.
2. 최초 사용자 제출 proof: 사용자 수용 여부, 주요 부족점, 화면의 전체 완성도와 제출 전 모든 탐색·수정 이력.
3. 필요한 수리 후 최종 결과: 사용자 품질 선호, 남은 결함, 기능/상태/모바일 완성도, 원본 의도 보존. 미완료로 중지한 run도 결과에 포함한다.

가능한 경우 도구 이름과 구현자 설명을 가리고 같은 크기·콘텐츠·상태로 비교한다. 평가 항목은 구도/시선 흐름, 타이포/간격, 이미지, 고유성/제품 적합성, 상태/반응형 craft다. 근거 없는 종합 미감 점수를 만들지 않고 pairwise 선호, 수용/거절, 이유를 기록한다. 실행 순서와 반복 run도 기록해 우연히 좋은 결과 한 번으로 결론 내리지 않는다.

기능/접근성/제품 의미는 품질과 교환할 수 없는 제약이다. 첫 화면이 더 아름다워도 필수 흐름이 깨졌으면 성공으로 처리하지 않는다. 첫 proof와 최종 결과, 미완료·실패 run도 모두 남긴다. 후보를 여러 개 만들었으면 선택본 외 후보와 선택 이유를 보존한다.

평가 기준·필수 조건·과제 묶음·중지 조건은 실행 전에 고정한다. 개발/보정에 사용한 화면과 held-out 평가 화면을 분리하고, 같은 화면의 crop/상태/viewport 변형을 양쪽에 나누지 않는다. Critic 보정 평가와 Harness 품질 비교도 별개의 결과로 보고한다. 같은 결과를 보고 기준을 바꾸면 탐색 결과로 남기고 새 보류 자료로 확인한다.

초기 과제 둘 이상의 결과는 제한된 feasibility 증거다. 범용 품질 우월성을 주장하려면 대상 도메인·언어·콘텐츠·상태의 범위를 넓히고 반복 결과의 불확실성을 보고해야 한다. 최소 과제 수를 통과 보증으로 사용하지 않는다. 성공 사례만 따로 선별하지 않고 실패/무승부/선호 불일치와 사용자 발견 결함을 함께 공개한다.

토큰·시간·호출 수는 설명용 지표이며 최소화 목표가 아니다. 성공은 더 높은 실제 품질과 더 적은 중요 결함/허위 완료로 판단한다. 문서의 양, 자체 PASS 개수, 시행한 스킬 수는 성과가 아니다.
