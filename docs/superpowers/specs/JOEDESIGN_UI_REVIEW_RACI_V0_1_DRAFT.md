이 문서는 설계 근거와 역할 경계를 보존한다. 실행 가능한 현재 기능은 저장소의 `skills/joedesign-harness/`와 테스트를 기준으로 확인한다. §13의 제작 원칙 중 자동화되지 않은 판단은 구현자의 실제 화면 관찰이 필요하다. 상세 조사 근거는 [디자인 도구 조사 보고서](JOEDESIGN_DESIGN_TOOL_RESEARCH_2026-09-29.md)에 있다.

## 현재 채택 결정과 검증 경계 (2026-09-30)

기존판은 5개 결함의 별도 탐지·수리 비교와 실제 파일 수정 과제의 사전 고정된 6개 문제에서 개선안과 같은 결과를 냈다. 두 비교 모두 한정된 과제이므로 일반적 동등성은 증명하지 않는다. 두 번째 과제에서 개선안의 모바일 조작부 줄바꿈 결함이 남았고, 반대로 데스크톱 사진은 조금 크게 사용했다. 이 혼합 결과로 우월성을 주장할 수 없다. 현재 설치본을 교체하지 않는 것이 사용자의 결정이다. 세부 기록은 [채택 판단](../../../evals/harness-v0.1/retention-decision.md)을 따른다.

CLI의 로컬 산출물과 합성 테스트는 실제 미감, 호스트 인증, 사용자 승인을 증명하지 않는다. 이 패키지에는 인증된 호스트 receipt 서비스가 없으므로 로컬 실행만으로 최종 APPROVED를 발행하지 못한다. 시각 품질과 사용자 수용은 실제 결과의 독립 관찰로 별도 판단한다.

## 0. 최상위 목표 — 사용자 결정 반영

제1 목표는 실제 결과물의 디자인 완성도와 퀄리티다. 토큰 절약, 호출 수 최소화, 조기 종료는 목표가 아니다. 필요한 참조 조사, 화면 비교, 교차검사, 수정과 재검증을 비용 절약만으로 생략하지 않는다.

정직한 보고는 품질과 교환할 수 없는 제약이다. 목표 품질에 도달하지 못하면 미달로, 확인하지 못했으면 미검증으로 보고한다. 보기 좋은 결과도 기능·접근성·제품 의미의 필수 요구를 위반하면 전체 완료가 아니다.

토큰·시간은 관찰 지표로 기록한다. 동일 근거의 무의미한 재조회, 이미 해소된 finding의 중복 작성, 가설 없는 반복 수정은 줄이되, 더 나은 품질이나 더 확실한 판단에 필요한 작업은 수행한다. 향후 사용자가 명시적 시간/예산 상한을 정해도 도달하지 못한 품질을 PASS로 바꾸지 않는다.

이 결정은 기존 인계안과 스킬 기본값의 비용 우선 해석보다 우선한다. 자동화된 차단 범위는 실제 CLI와 테스트에서 확인된 것에 한정한다.

### 0.1 문서 권위와 개정 범위

이 문서가 원본 인계안에 대한 현재 설계 변경안이다. 충돌하는 설계 항목은 이 문서의 명시적 변경을 적용하며, 언급하지 않은 원본 요구는 유지한다. 조사 보고서는 근거와 추론을 설명하는 참고 문서다. 두 문서 모두 사용자의 명시적 결정, 승인된 프로젝트 DESIGN.md와 제품 요구를 덮어쓰지 않는다. 프로젝트 시각 승인이 Harness 운영 정책 전체의 승인이라는 뜻도 아니다.

원본의 단일 순차 상태는 §14의 candidate별 상태와 gate 규칙으로 구체화한다. 현재 소스의 실행 가능 범위와 차이는 CLI 및 테스트로 확인한다. 원본 파일, JOEDESIGN v0.2, 설치 스킬, JOENESS는 이 문서 정리로 수정하지 않는다.

## 1. 목적과 범위

여러 스킬의 전문성이 겹친다는 전제에서, 제작과 검사 항목마다 1순위 책임자와 2·3순위 교차검사자를 정한다. 생성 전에 실제 자원과 품질 기준을 연결하고, 탐색·대표 화면·국소 수정을 통해 완성도를 높인다. 같은 화면을 모든 스킬이 처음부터 끝까지 다시 검사하거나, 한 스킬의 취향이 승인된 방향을 바꾸는 일을 방지한다.

핵심 스킬은 JOEDESIGN, Impeccable, UI UX Pro Max, Vercel web-design-guidelines다. 이미 설치된 React Best Practices와 Optimize Web Animations는 해당 구현/성능 문제가 있을 때만 담당한다. OMD는 참조 자료이며 검사자나 승인권자가 아니다.

스킬은 역할에 적용할 지침이다. 스킬을 바꿔 읽는 것만으로 독립된 검수자가 생기지 않는다. Independent Critic은 실행 컨텍스트를 별도로 분리해야 한다.

이 문서는 설계·책임·검증 경계를 기록한다. 제안형 표현은 당시 설계 경위를 나타내며, 현재 실행 가능 여부는 위 채택 결정과 패키지 코드가 우선한다. 승인된 프로젝트 DESIGN.md를 대체하지 않는다.

## 2. 방식 선택

검토한 방식:

1. 모든 스킬의 전체 감사: 관점은 늘지만 동일 결함의 반복과 상충하는 기본값이 실질적 품질 문제를 가릴 수 있다.
2. 스킬별 완전 독점: 경계에 걸친 결함과 자기검증을 놓치기 쉽다.
3. 항목별 단일 책임 + 품질 필요에 따른 교차검사: 권장. 1순위가 해당 항목의 검사와 판정 초안을 책임지고, 2·3순위는 독립적인 근거와 다른 관점으로 보완한다. 호출 수 제한을 위한 분배가 아니다.

순위는 발언권이나 진실의 서열이 아니다. 근거 있는 FAIL은 어느 순위가 발견해도 처리해야 한다. 다수결과 점수 평균은 사용하지 않는다.

## 3. RACI 정의

- R (Responsible): 해당 작업을 실제 수행하고 증거와 판정 초안을 작성한다.
- A (Accountable): 그 작업 결과의 책임과 결정권을 가진 단일 역할이다.
- C (Consulted): 정해진 쟁점에 대한 교차검사/자문을 수행한다.
- I (Informed): 결과를 전달받는다. 같은 검사를 반복할 의무는 없다.

검사 순위 표의 1순위는 R, 2순위는 C1, 3순위는 C2다. A는 별도 운영 RACI에서 지정한다. C1/C2는 R을 자동으로 대체하는 대기 순번이 아니다.

## 5. 운영 RACI

아래 표는 작업 결과별로 A를 하나만 둔다. 별도 agent 수를 강제하는 조직표가 아니다.

| 작업 결과 | A | R | C | I |
|---|---|---|---|---|
| 적용할 규칙·대상·검증 방법 확정 | Harness controller | 항목별 1순위 검사 역할 | 필요한 2·3순위, Product 담당 | 구현자, Critic |
| 프로젝트 시각 품질 기준안 | JOEDESIGN 담당 | JOEDESIGN 담당 | Impeccable, 사용자 brief, Product 담당 | Harness, 구현자, Critic |
| 코드 변경·수정 결과 | 구현 책임자 | 구현자 | 해당 finding 담당, J | Harness, Critic |
| 실제 브라우저·상태 증거 수집 | Harness controller | 구현자/브라우저 실행 역할 | 해당 검사 담당 | Critic |
| 항목별 검사 보고서와 미검증 범위 | Harness controller | 항목별 1순위 검사 역할 | 실행 조건에 해당하는 C1/C2 | 구현자, Critic |
| 독립 Visual Internal 판정 | Independent Critic | 독립 검수 실행 역할 | 원본/규칙 자료; 구현자에게는 사실 확인만 | Harness, 구현자, 사용자 |
| 증거·결함에 따른 gate 상태 전이 | Harness controller | gate validator/실행 역할 | Critic, 검사 담당 | 구현자, 사용자 |
| 제품 의미·범위의 변경 결정 | 사용자/지정 Product authority 중 1인 | Product 담당 | J, 영향받는 검사 담당 | Harness, 구현자, Critic |
| 정확한 결과물의 시각 승인 | 사용자 | Harness가 검토 패키지 제출 | Critic, J | 구현자, 관련 검사 담당 |

Harness의 A는 증거 충족과 절차에 대한 책임이다. 시각 취향을 새로 정하거나 검수 FAIL을 근거 없이 PASS로 바꿀 권한이 아니다. Critic도 제품 의미나 승인된 방향을 변경할 수 없다.

## 6. 각 스킬의 권한 경계

### JOEDESIGN

승인 원본의 관계를 프로젝트에 번역하고, 구도·이미지·반응형 의도·토큰 의미·범위 변화를 검사한다. 제품 의미와 사용자 승인은 소유하지 않는다. 하위 검사자가 발견한 기능/접근성 결함을 '원본과 같다'는 이유로 무효화할 수 없다.

### Impeccable

로컬 craft와 시각 상태, 모션 표현을 주도한다. 구현 전 후보별 계약 안에서 타이포·간격·아이콘·모션 조합을 검토하고, 구현 후 실제 결과를 다듬는다. polish/typeset/layout/adapt 등 필요한 지침을 해당 역할에 맞게 사용한다. 새 구도, bolder/새 방향, Product 문구 변경, DESIGN.md 재작성은 craft 권한에 포함되지 않는다.

현재 audit의 점수 합계는 Harness PASS로 환산하지 않는다. 규칙에서 발견한 결함을 증거 단위 PASS/FAIL/UNVERIFIED로 정규화한다. 점수나 광범위한 개선 메뉴가 별도 방향 변경을 허가하지 않는다.

upstream의 고정 검사 횟수/비용 절약 지침은 이 Harness의 품질 상한으로 사용하지 않는다. 한 번의 검사와 확인만으로 남은 결함이 사라지는 것은 아니다. 필요한 추가 검사와 수리는 근거를 갖고 계속하며, 반복 실패는 아래의 재진단 규칙을 따른다.

### UI UX Pro Max

필요한 UX outcome을 --domain으로 검색하고 스택 구현 규칙은 --stack으로 조회한다. 폼/피드백/긴 콘텐츠/컴포넌트 의미를 보완한다. 결과는 제안이며 플랫폼 적합성과 근거를 확인한다.

Harness 경로에서 --design-system/--persist 자동 실행과 별도의 MASTER.md authority 생성은 사용하지 않는 정책을 제안한다. 업종별 색상·서체·레이아웃 추천이 Reference Lock이나 승인 DESIGN.md를 대체하지 않게 한다. 기존 upstream 스킬 파일은 수정하지 않고 호출 어댑터의 역할 경계로 명시한다.

### Vercel web-design-guidelines

웹 구현의 의미, 키보드/포커스, 폼 연결, 콘텐츠 내구성, 모션·반응형 결함을 검수한다. 파일/행 지적만으로 실제 동작 PASS를 주장하지 않는다. 네이티브 시맨틱으로 충족되는 동작에 불필요한 키보드 핸들러를 강제하지 않는다.

영문 Title Case, 일괄 autocomplete 설정, 리스트 길이 하나만으로 가상화 강제 등은 보편적 실패 조건으로 승격하지 않는다. 프로젝트 언어·사용 목적·실제 비용에 따라 적용 여부를 정한다.

### 조건부 성능 전문 스킬

React Best Practices는 실제 React/Next 프로젝트에만 적용한다. Optimize Web Animations는 해당 모션/RAF/캔버스/장기 실행 문제가 검사 대상일 때만 적용한다. 성능 개선을 위해 승인된 표현이나 필요한 상호작용을 무단 제거하지 않는다.

## 7. 규칙을 채택하는 기준

규칙마다 먼저 종류를 구분한다.

1. REQUIRED: 계약상 필요한 기능/상태, 적용 가능한 접근성 기준, 명시적 프로젝트 제약. FAIL 또는 UNVERIFIED이면 해당 gate 통과 불가.
2. CONTRACT: 승인된 또는 작업 대상으로 명시한 시각 관계·토큰·모션. 아직 승인되지 않은 작업 계약은 proposal 상태를 유지한다. 계약 충실도 PASS와 사용자 승인은 별개다.
3. ADVISORY: 일반적인 미감/프레임워크/업종별 권장사항. 불일치만으로 gate를 막지 않는다. 채택할 경우 이유와 범위를 명시한다.

상위 근거는 사용자/제품의 명시적 요구와 승인된 프로젝트 시각 authority다. 접근성·기능 요구와 승인된 시각 타깃이 충돌하면 둘 중 하나를 조용히 버리지 말고 충돌을 드러낸다. 일반 스킬의 기본값은 이 근거들을 덮어쓰지 않는다.

검사를 시작할 때 사용한 스킬 버전 또는 파일 hash와 외부 규칙 snapshot/hash를 기록한다. Vercel 규칙은 review 시작 시 최신 원문을 가져오되 동일 review의 재검사는 같은 snapshot을 쓴다. 도중 업데이트는 규칙 변경으로 별도 기록한다.

## 8. 1·2·3순위 실행 조건

- 1순위: scope 내 적용 항목을 모두 검사한다. 근거 없는 항목은 UNVERIFIED로 남긴다. 개별 규칙뿐 아니라 전체 화면의 품질을 해당 담당이 확인한다.
- 2순위: material 디자인/재설계에서는 모든 적용 시각 품질 항목을 교차검사한다. 필수 접근성/입력 경로, 공유 컴포넌트/전역 스타일 영향, 이전 실패 항목도 필수다. 국소 변경도 품질 불확실성이 있으면 실행한다. 1순위가 PASS라는 이유로 생략하지 않는다.
- 3순위: 판정 충돌, 책임 경계, 반복 실패뿐 아니라 품질 판단의 근거가 약하거나 다른 전문 관점으로 확인할 미해결 문제가 있을 때 실행한다. 횟수/비용 때문에 필요한 검사를 생략하지 않으며, 매번 검사의 질문과 대상을 명시한다.
- 실행하지 않은 C는 NOT_RUN으로 기록한다. 그 자체를 제품 결함 UNVERIFIED로 바꾸지는 않는다. 단, 필수 교차검사가 누락되면 review gate는 미완료다.
- 1순위 사용 불가: Harness가 역량을 확인하여 재배정 사실/이유를 남기거나 해당 검사를 UNVERIFIED로 유지한다. 낮은 순위의 PASS를 자동 승계하지 않는다.
- 같은 결함을 여러 스킬이 찾으면 target + rule/claim + state 기준으로 하나의 finding에 근거를 합친다. 결함 수와 수정 작업을 중복 계산하지 않는다.

독립 Critic은 C1/C2를 수행했다는 사실로 대체되지 않는다. 필수 claim, 실제 원본/스크린샷과 상태 증거를 별도로 검토한다. 스킬별 숫자 점수나 구현자의 자기평가는 기본 입력에서 제외한다.

동일 원인에 대한 국소 수정 2회 후에도 material FAIL이면 그 접근을 중단하고 참조 해석·구도·asset·계약 자체를 재진단한다. 이는 품질 작업 전체의 종료나 PASS 사유가 아니다. 새로운 근거/수리 가설로 다시 진행하며, 승인 방향이나 범위의 변경이 필요할 때만 해당 결정권자에게 올린다. 전체 반복 횟수의 임의 상한은 두지 않는다.

재진단 이후에도 실행 가능한 새 가설이나 자원이 없으면 §13.10에 따라 미해결 상태로 종료·대기한다. 무제한 반복을 요구하지 않으며, 반복을 멈췄다는 사실은 완료 판정이 아니다.

## 9. 충돌 해결

1. 동일 버전·surface·viewport·state를 비교하는지 확인한다.
2. 규칙이 REQUIRED/CONTRACT/ADVISORY 중 무엇인지, 실제로 적용되는지 확인한다.
3. 코드/DOM로 확인할 사실, 동작 관찰, 시각 판단을 분리한다.
4. 재현 가능한 결함은 발견 순위와 무관하게 유지한다. 1순위는 반증 또는 수정·재검사로만 해소한다.
5. 3순위는 해당 쟁점만 조사한다. 투표로 판정하지 않는다.
6. 적용성/사실이 불분명하면 UNVERIFIED. 계약 충돌은 해결될 때까지 관련 gate를 막고, 제품/방향 변경만 해당 authority에 올린다. 무관한 작업은 계속한다.

예시: J는 버튼이 원본과 일치한다고 PASS하고 V는 키보드 이름 누락을 FAIL할 수 있다. 서로 다른 claim이므로 둘 다 유지한다. 같은 외형을 보존하면서 의미를 고친 후 V 항목과 영향을 받은 시각 영역을 재검사한다.

예시: U가 업종 추천 파란색을 제시해도 승인 팔레트를 어겼다는 결함으로 만들지 않는다. 해당 추천은 ADVISORY이며 채택하지 않아도 실패가 아니다.

예시: I는 모션이 자연스럽다고 PASS하고 M은 화면 밖 RAF가 계속 실행된다고 FAIL할 수 있다. 표현 PASS는 유지하되 성능 항목은 수리 전까지 FAIL이다.

## 10. 검사 기록과 gate

새 필수 산출물을 늘리기보다 기존 DESIGN_CONTRACT에 적용 규칙을, CRITIQUE에 finding을, EVIDENCE_MANIFEST에 실행/근거를 추가한다.

최소 기록:

- claim/rule ID, 규칙 종류, 적용 이유, source/version
- target: 구현 revision 또는 콘텐츠 fingerprint, route/surface, viewport, state/theme/locale
- primary reviewer, consulted reviewers, actual execution context
- expected, observed, evidence pointer
- PASS/FAIL/UNVERIFIED, severity(우선순위일 뿐 합산 점수 아님)
- resolution 또는 좁은 예외의 근거/결정권자
- 수정 후 영향을 받은 증거의 무효화 및 재검사 상태

gate 규칙:

- 필수 finding 하나라도 FAIL이면 해당 category FAIL.
- 필수 FAIL이 없더라도 필수 관찰/검사가 빠지면 UNVERIFIED.
- 전부 관찰되고 충족된 category만 PASS.
- ADVISORY 미채택과 적용 대상이 아닌 항목은 이유를 기록하며 PASS 수에 더하지 않는다.
- 코드 변경 후 영향을 받은 기존 screenshot/동작 증거는 STALE 처리하고 현재 revision의 재관찰로 갱신한다. 영향 없는 증거의 재사용도 범위 근거를 남긴다.
- Technical/Accessibility/Responsive/Craft/Visual Internal/User Acceptance는 독립 상태다. 하나의 PASS가 다른 상태로 전파되지 않는다.
- Critic unavailable 또는 해당 품질 범위의 calibration이 미확인일 때 Visual Internal PASS 불가(§10.3). 사용자에게 한계를 표시한 현재 증거를 제출할 수는 있다.
- USER ACCEPTANCE는 정확한 결과물의 사용자 승인으로만 변경한다.

### 10.1 규칙 준수와 시각 품질의 별도 판정

규칙 준수는 품질의 하한이다. 규칙과 Reference Lock을 충실히 따랐다는 사실만으로 디자인 완성도를 PASS하지 않는다. 기존 DESIGN_CONTRACT에 다음 품질 기준을 구현 전에 구체적으로 기록한다.

- 제품 목적이 읽히는 첫 시선과 다음 행동/읽기 흐름
- 타이포 위계, 실제 언어의 줄바꿈, 간격·밀도·광학 정렬의 완성도
- 실제 이미지/콘텐츠의 품질과 구성에서 맡는 역할
- 컴포넌트·상태·테마·화면 간 표현의 일관성
- 모바일에서 독립적으로 성립하는 구도와 조작성
- 제품과 무관한 반복 템플릿 구성이 의미와 개성을 희석하는지

구체적인 목표 관계와 참조 근거를 사용하며 '프리미엄', '예쁘다' 같은 형용사만으로 기준을 만들지 않는다. 카드/그라디언트 등 특정 문법 자체를 일괄 금지하지 않는다. 렌더를 본 뒤 통과시키기 위해 기준을 낮추지 않는다. 초기 기준이 불충분하면 계약 개정과 영향 재검증을 기록한다.

독립 Critic은 최소 두 결과를 분리한다.

1. Contract Conformance: 잠긴 관계를 구현했는가.
2. Visual Quality: 위 품질 기준을 실제 화면 전체와 디테일에서 충족했는가.

둘 모두 현재 대상에 대한 근거와 §10.3의 검수 조건이 있어야 Visual Internal PASS가 가능하다. 계약은 지켰지만 결과의 위계·리듬·완성도가 미달이면 Conformance PASS / Quality FAIL이 가능하다. 사용자 승인은 이 둘과도 별개다.

Critic은 관찰한 품질 결함을 위치·상태·영향·기준과 연결해 설명하며 새 디자인 방향을 직접 적용하지 않는다. 계약 자체가 품질을 방해하면 이를 드러내고 JOEDESIGN의 재합성으로 돌린다. 승인된 방향의 변경 권한은 기존대로 사용자에게 있다.

### 10.2 허위 완료를 막는 실행 구조

이 항목은 구현 요구사항이다. 스킬 문구만으로 에이전트의 모든 허위 발언을 막을 수 있다고 주장하지 않는다.

- 증거 수집 경로와 판정 기록 경로를 분리한다. 브라우저/테스트 실행 기록에서 실행 ID, 실제 URL/viewport/state, 결과물 fingerprint, 파일 hash를 수집한다. 에이전트가 적은 Observed: YES 또는 파일 존재만으로 관찰을 인증하지 않는다.
- 이미지 경로뿐 아니라 실제 파일을 열어 대상/화면/상태를 확인한다. 동작 claim에는 입력 동작과 그 결과의 관찰 기록이 필요하다. 여기에 연결할 근거가 없으면 UNVERIFIED다.
- 독립 검수의 실제 실행 식별자를 기록한다. 별도 실행 없이 Critic 문서만 작성한 경우 독립 검수로 인정하지 않는다.
- gate validator가 현재 버전, required matrix, 남은 finding, 필수 교차검사, Critic 결과를 확인하여 구조화된 상태를 산출한다. 필수 항목 누락이나 기록 간 불일치는 통과를 막는다.
- 공식 handoff의 상태/관찰 범위는 검증 결과에서 생성한다. 서술형 보고가 상태를 더 좋게 표현하거나 미검증 route까지 확대하면 handoff를 거부한다. 가능한 한 상태 칸은 자유 서술 대신 정해진 값으로만 출력한다.
- 발견된 FAIL을 삭제하거나 필수 대상을 OUT_OF_SCOPE로 바꿔 통과시키지 않는다. 변경 이유, 전후 범위, 권한 근거를 보존한다. 필수 요구의 실질적 완화는 사용자/해당 authority 결정이 필요하다.
- 실행 실패, 도구 부재, 접근 불가, 빈 결과를 PASS로 대체하지 않는다. 과거 정상 실행을 현재 실행 결과처럼 재사용하지 않는다.
- 사용자 승인은 정확한 결과 버전/범위와 실제 사용자 메시지 근거에 연결한다. 구현자나 Critic이 대신 승인 기록을 생성할 수 없다.
- IMPLEMENTATION_COMPLETE는 구현·테스트 범위의 완료만 뜻한다. 실제 디자인 품질 검증, 사용자 승인, 운영 A/B 검증, PRODUCTION_READY로 자동 승격하지 않는다.

보장 범위: 파일 hash는 동일성 확인이지 관찰의 진실성 증명이 아니다. 모든 기록을 동일 에이전트가 자유롭게 수정할 수 있으면 완전한 위조 방지가 아니다. 실행 호스트가 보존하는 도구 로그와 분리된 validator 경로를 우선 사용하고, 구현 수준에서 검증 가능한 것만 차단 효과로 보고한다. 설계 문서만 존재하는 현재 단계에서 '허위 완료를 차단했다'고 보고하지 않는다.

### 10.3 Critic의 독립성과 평가 보정

별도 컨텍스트는 구현자의 설명에 끌리는 위험을 줄이는 조건일 뿐, 미감의 정확성을 보장하지 않는다. 같은 모델의 공통 편향도 남는다. 모델 수를 늘리거나 스킬 이름을 달리한 것을 calibration으로 세지 않는다.

- Critic 입력은 brief, 고정한 계약/규칙, 현재 결과, 참조, 실제 상태 증거다. 구현자의 자기 점수·선택 선호·성공 주장과 다른 검수자의 결론은 초기 독립 판정 후에만 대조한다. 동일 환경을 재관찰할 수 없으면 관찰 범위를 한정한다.
- 보정 자료는 실제 사용자/지정 디자인 검토자가 수용·거절한 결과와 구체적인 이유다. 출처, 화면/언어/제품 유형, 당시 기준과 revision을 보존한다. 사용자 선호와 필수 기능·접근성 판정을 섞지 않는다.
- 보정 예시와 평가용 보류 자료를 분리한다. 평가용 결과의 정답·선호는 판정 전 Critic에게 숨긴다. 동일 화면의 crop/viewport 변형도 같은 묶음으로 분리하여 유출을 막는다. 같은 출력에 자신이 매긴 평가를 정답으로 재사용하지 않는다.
- 실제 평가에서는 잘못 통과시킨 중요한 결함, 놓친 결함, 잘못 거절한 결과, 사용자와의 선호 불일치를 각각 기록한다. 취향 차이를 모두 오류로 간주하지 않으며 계약 밖 개선 의견은 ADVISORY다. 샘플 수와 불확실성을 공개하고 임의의 '신뢰도 95%'를 붙이지 않는다.
- `calibration_status`는 UNCALIBRATED / IN_SCOPE / OUT_OF_SCOPE다. IN_SCOPE는 구현자가 선언할 수 없다. 독립 평가 담당이 보류 자료 결과를 제출하고 사용자/지정 디자인 authority 중 1인이 대상 범위·허용할 오류·남은 한계를 명시하여 승인해야 한다. 평가 전에 기준을 정하며 모델·규칙·주요 도메인 변경은 재평가한다. 근거 없는 범용 인증은 금지한다.
- 초기에는 UNCALIBRATED가 정상이다. 제작과 수정은 진행하고 구체적 결함·계약 적합성을 검토한다. 재현된 필수 품질 결함이 있으면 Quality/Visual Internal은 FAIL이다. 결함을 못 찾았다는 이유만으로 정식 PASS를 만들지 않으며, 이때는 UNVERIFIED로 둔다. 어느 경우에도 한계를 표시해 사용자에게 현재 화면을 제출할 수 있다. 실제 사용자 승인은 별도 기록되고 내부 검수의 미검증/실패를 지우지 않는다.

책임: calibration 자료/분리/평가 기록은 평가 담당 R, 사용자/지정 디자인 authority 중 1인 A, J·I·U는 C다. 제작자나 해당 Critic은 자신의 평가 보정을 최종 승인하지 않는다. Critic은 적용 가능한 범위 안에서만 §5의 판정 A를 맡는다. 이 설계는 사용자 평가가 쌓이기 전 자동 품질 인증을 유보하며, 화면 제작을 막기 위한 선행 조직 구축을 요구하지 않는다.

### 10.4 증거의 신뢰 경계

증거 내용, 수집 출처, 적용 범위는 따로 검증한다. '서명/해시가 있다'와 '올바른 화면을 실제로 봤다'를 동일시하지 않는다.

| 증거 등급 | 필요한 근거 | 허용되는 주장 |
|---|---|---|
| DECLARED | 에이전트가 작성한 manifest/설명 | 수행했다고 보고됨; 실행/관찰 인증 불가 |
| INSPECTED | 실제로 열어 본 파일과 관찰 기록 | 해당 파일에 보이는 내용; runtime 실행·사용자 승인 인증 불가 |
| HOST_OBSERVED | 구현자가 수정할 수 없는 호스트 기록에서 조회한 실행 receipt와 원본 출력의 연결 | 그 실행에서 확인된 대상·동작·결과만 인증 |

최종 동작·실행·독립 검수 claim은 HOST_OBSERVED 근거를 요구한다. 외부 참조 이미지처럼 실행 claim이 아닌 입력은 INSPECTED로 충분할 수 있다. 높은 등급도 다른 route/state나 실제 백엔드를 증명하지 않는다. 호스트가 로그의 변경 방지나 별도 실행 식별을 제공하는지는 구현 시작 시 실제 capability로 확인한다. 충족하지 못하면 해당 claim은 UNVERIFIED이고 '위조 방지 완료'를 주장할 수 없다.

수집기는 `run_id`, `candidate_id`, source/build revision, 콘텐츠·fixture·asset·font 식별자, 실제 URL/viewport/state/theme/locale, 수집 시점, action/result, 원본 출력 위치를 연결한다. 상태 이름은 구현자가 붙인 라벨만 믿지 않고 DOM/관찰 결과와 대조한다. 변경 중 캡처, run이 섞인 증거, 결과 식별 불가, stale receipt는 거부한다. 비결정적 데이터는 해당 실행 snapshot에 범위를 묶는다.

validator는 에이전트가 쓴 최종 verdict를 입력 정답으로 쓰지 않는다. 신뢰된 기준 버전의 required coverage·상태 predicate와 호스트 receipt를 대조하고 구조화된 결과를 계산한다. 에이전트가 자기 실행에서 validator/기준/receipt를 함께 고쳐 통과시킬 수 있는 배포는 신뢰 경계가 성립하지 않는다. 그런 변경은 별도 변경 검토와 재검증 대상이다. 단순히 다른 파일이나 프로세스로 나누는 것으로 해결했다고 보고하지 않는다.

사용자 승인도 실제 사용자 event/message의 출처와 exact candidate/revision/scope를 조회해야 한다. 에이전트가 임의로 넣은 `approved: true`는 효력이 없다. 진짜 승인 메시지가 있어도 대상이 모호하면 해당 승인은 미확정이며, 과거 승인 이후 변경된 영역은 다시 승인 대상이다.

공식 handoff의 gate 상태는 validator 결과에서 생성하고 보고의 범위가 그 결과를 넘으면 발행을 거부한다. 일반 채팅의 모든 자유 서술을 기술적으로 막는다고 보장하지 않는다. 보고서 일관성 검사, 실행 기록의 무결성, 미감 판단의 정확성은 서로 다른 검증 대상이다.

## 11. 설계 확인 시나리오

구현 시 검증할 동작이며 현재 자동화된 테스트는 아니다.

1. I와 J가 PASS해도 V의 재현 가능한 필수 접근성 FAIL은 gate를 막는다.
2. U의 업종 팔레트 추천이 승인된 팔레트를 변경하지 못한다.
3. 3개 스킬이 같은 badge overflow를 찾으면 finding 1개로 합쳐진다.
4. 1순위가 없어도 2순위 결과를 자동 PASS로 승계하지 않는다.
5. 스킬을 바꿔 읽은 동일 구현 컨텍스트를 independent critic이라고 기록하지 않는다.
6. React가 아닌 프로젝트에서 React 검사를 요구하지 않는다.
7. 국소 타이포 수정에 전체 성능 감사/전체 UX 재검토가 자동 실행되지 않는다.
8. 공유 CSS 변경은 2순위 교차검사와 영향받는 보호 영역의 재관찰을 요구한다.
9. 수정 전 스크린샷은 영향을 받은 수정 후 claim의 증거로 통과하지 못한다.
10. Impeccable 점수 상승이나 세 스킬의 다수결로 PASS가 생성되지 않는다.
11. Contract Conformance PASS라도 실제 Visual Quality FAIL이면 Visual Internal PASS가 생성되지 않는다.
12. 토큰/호출 수를 줄이려고 필요한 시각 교차검사를 생략하면 해당 review를 완료로 표시하지 못한다.
13. 국소 수정 2회 후 미달이면 재진단으로 전환하며 완료로 종료하지 않는다.
14. 존재하지 않는 screenshot, 다른 route/state의 이미지, 실행 로그 없는 Observed: YES는 증거 검증에서 거부하거나 UNVERIFIED로 남긴다.
15. 실제 독립 실행 없이 작성한 CRITIQUE는 independent review로 통과하지 못한다.
16. 필수 state를 보고 직전에 삭제하거나 OUT_OF_SCOPE로 바꾸면 범위 변경 근거 없이는 통과하지 못한다.
17. 구조화된 결과가 UNVERIFIED인데 공식 handoff가 '전체 검증 완료'라고 출력하면 거부한다.
18. 설치·스키마·단위 테스트만 성공한 상태에서 디자인 품질 향상이나 운영 검증 완료를 주장하지 못한다.
19. 탐색 후보 A/B의 참조 owner가 섞이지 않고, 각 후보는 자기 계약·증거에만 연결된다.
20. 대표 화면만 관찰한 상태에서 다른 route/state를 PASS로 승격하지 못한다.
21. 동작하는 컴포넌트 소스가 없거나 font/asset이 검증되지 않은 대체본인 상태를 실제 자원 연결 완료로 보고하지 못한다.
22. 후보 선택을 exact user acceptance로 기록하지 못한다.
23. 탐색용 fixture로 동작한 화면을 production 데이터/백엔드 검증으로 보고하지 못한다.
24. 콘텐츠·상태가 맞지 않는 인기 참조는 키워드 일치로 선택되지 않으며, 원본 관계→변환→반증 조건 없는 후보는 CONTRACT_READY로 넘어가지 못한다.
25. 타이포·이미지·모션의 개별 검사를 통과해도 통합 화면의 위계가 실패하면 전체 품질은 FAIL이다.
26. UNCALIBRATED Critic이 결함을 못 찾아도 Visual Internal은 UNVERIFIED이며 제작·사용자 검토는 가능하다.
27. 보정 예시가 보류 평가 자료에 섞이거나 모델/도메인이 바뀌면 해당 calibration을 그대로 승계하지 못한다.
28. 중요 이미지가 placeholder이거나 한글 폰트가 의도하지 않은 fallback이면 자원 검증 완료와 최종 품질 PASS가 생성되지 않는다.
29. manifest·스크린샷 hash·validator를 같은 실행자가 바꿀 수 있으면 HOST_OBSERVED로 인정하지 않는다. 신뢰된 경로가 없으면 미검증을 유지한다.
30. 각 수정은 가설·같은 조건의 전후 결과·회귀 확인으로 판정한다. 실행 가능한 새 가설이 없으면 미해결로 멈추며 PASS로 바뀌지 않는다.
31. 모든 필수 gate가 PASS여도 정확한 사용자 승인 전 APPROVED가 되지 않는다. 반대로 사용자 선호 승인이 있어도 미검증 gate가 자동 PASS되지 않는다.
32. 보고서의 최초 proof 이전에 생성한 실패 화면·폐기 후보도 최초 render 및 전체 run 기록에서 빠지지 않는다.
33. 특정 route만 승인되면 그 scope만 승인되며, 다른 route 확장이나 승인 후 asset/폰트 교체가 기존 승인을 승계하지 못한다.

위 목록은 테스트 명세다. 구현 시 원본 F1–F12와 함께 각 요구를 실행 가능한 테스트 ID/실제 결과에 연결한다. 파일 파싱·스키마 검사 통과와 위 시나리오의 실제 통과를 구별한다.

## 13. 조사에 따른 제작 단계 보완

이 절은 기존 순차 pipeline을 보완하는 설계 변경안이다. 동일 scope에서 일찍 참조 하나를 최종 확정하고 끝까지 구현하는 흐름을, 필요 시 후보를 비교한 뒤 확장하는 흐름으로 바꾼다. 원본 인계 파일은 보존한다.

### 13.1 제작 흐름

제품 의도·실제 콘텐츠 → 승인 원본/기존 코드/asset 확인 → 사용할 component·token·font·사용 예시 연결 → 승인 타깃이 있으면 보존 구현, 미정이면 후보별 탐색 → 실제 대표 화면의 구도·craft·좁은 화면·핵심 상태 확인 → 선택 방향과 계약 확정 → route/흐름 확장 → 요소 단위 정밀 수정 → 독립 검수 → 현재 증거에 한정된 보고 → 사용자 승인.

이는 Figma Make의 Make kits, Stitch의 탐색/수정 분리, v0의 실제 starter 검토에서 도출한 JOEDESIGN 설계 추론이다. 경쟁 도구의 내부 알고리즘을 복제하거나 성능 우열을 확인했다는 의미가 아니다.

### 13.2 참조 Lock과 탐색의 관계

- material code generation 전 계약 필요 원칙은 유지한다. 탐색 코드도 candidate ID, scope, 임시 Reference Lock, 간단한 구현 계약을 먼저 둔다.
- 각 후보 내부는 Primary 1개, Secondary 최대 2개, 동일 축 owner 1개 원칙을 지킨다. 후보끼리는 별도의 owner/계약/증거를 갖고 서로 평균내지 않는다.
- 후보별로 기존 REFERENCE_LOCKED → CONTRACT_READY → IMPLEMENTED 경로를 사용하되, 모든 artifact와 상태는 candidate ID에 귀속된다. final handoff는 선택된 candidate ID만 대상으로 한다. 후보 실행 수는 품질 질문에 따라 정한다.
- 이미 승인된 프로젝트 타깃은 Primary가 될 수 있다. OMD는 참조 검색원이지 기존 승인을 덮어쓰는 상위 권위가 아니다. 외부 참조 추가 자체를 필수 성과로 만들지 않는다.
- 후보 탐색 권한이 있는 작업은 되돌릴 수 있는 proof 제작을 진행한다. 후보 선택과 실제 결과물의 사용자 승인은 구분한다. 승인된 방향/범위의 변경이나 승인이 필요한 종속 확장에는 기존 승인 원칙을 적용한다.
- 방향 미달이면 선택을 보류하고 원인을 재진단한다. 후보를 만들었다는 사실이나 후보 중 상대적 1위라는 이유로 품질 PASS하지 않는다.

### 13.3 생성 자원과 대표 화면

설계 입력은 글로 된 규칙과 참조 이미지에 그치지 않는다. 실제 import 경로, component/prop/variant, token 사용 예시, font와 asset, 실제 문장/데이터 분포, 적용할 state를 연결한다. source에서 확인하지 못한 API나 스타일 값은 발명하지 않고 proposed/unknown으로 둔다.

초기 제품에는 거대한 디자인 시스템을 먼저 만들지 않는다. 이번 surface에서 필요한 자원만 실제로 구현·렌더해 확인한다. 새 UI 패키지, 자체 DB, 외부 도구 계정이 필수는 아니다.

대표 화면은 구도·타이포·이미지·밀도·주요 조작이 함께 드러나는 실제 runtime의 coherent slice다. 첫 hero나 버튼 모음만으로 전체 품질을 판정하지 않는다. 서사형 화면은 아래쪽 section 리듬을, 작업형 화면은 입력→결과/복구를 포함해 확인한다. 준비된 요소만 모아 어렵지 않은 화면을 대표라고 선택하지 않는다.

placeholder/fixture를 쓴 탐색은 명시할 수 있다. 다만 실제 이미지/폰트 미준비가 품질을 좌우하면 최종 완성 판정을 보류하고, fixture 결과를 실제 데이터 연동으로 표현하지 않는다. 대표 화면의 PASS는 그 scope만 증명한다.

### 13.4 제작 역할 RACI

| 작업 | 1순위 R | 2순위 C1 | 3순위 C2 | A |
|---|---|---|---|---|
| 참조 해석·후보 구도·대표 화면 선정 | JOEDESIGN | Impeccable | UI UX Pro Max | JOEDESIGN 담당 |
| 실제 component/API/token 연결 | 구현자 | JOEDESIGN | Vercel | 구현 책임자 |
| 초기 타이포·간격·아이콘·모션 조합 | Impeccable | JOEDESIGN | UI UX Pro Max | JOEDESIGN 담당 |
| 콘텐츠 길이·상태·복구 요구 준비 | UI UX Pro Max | Vercel | JOEDESIGN | Harness controller |
| 이미지 역할·asset 적합성·크롭 | JOEDESIGN | Impeccable | UI UX Pro Max | JOEDESIGN 담당 |
| 대표 화면의 비교·방향 선택 제안 | JOEDESIGN | Impeccable | UI UX Pro Max | JOEDESIGN 담당 |
| 요소별 정밀 수정 | 해당 검사 영역 R | 해당 C1 | 해당 C2 | 구현 책임자 |

이 표의 A는 작업/제안에 대한 책임이다. 제품 의미 변경, 독립 품질 판정, exact visual acceptance 권한은 §5 그대로다. Product에 없는 상태/기능을 U가 준비 과정에서 임의로 추가할 수 없다.

### 13.5 수정과 피드백

구체적인 요소/상태를 지정하고 원본과 현재 렌더의 차이를 확인한다. 변경 축, 원하는 관계, 유지할 주변 영역, 실제 source 위치를 연결한다. 코드 변경 후 같은 조건의 전후 렌더를 비교하고 영향을 받은 증거를 갱신한다.

최종 검사 전에도 최초 실제 화면, 대표 좁은 화면, 주요 흐름을 보고 필요한 피드백을 반영한다. 모든 중간 화면마다 사용자 승인을 요구하지 않으며, 미정인 방향/제품/범위 결정에 필요한 결과를 보여준다. Critic은 전체 화면과 확대 디테일 양쪽을 보고 판단한다.

### 13.6 산출물 연결과 검증

기존 산출물을 재사용한다: DESIGN_INTENT는 실제 콘텐츠/asset readiness, REFERENCE_CANDIDATES는 후보와 비교 축, REFERENCE_LOCK은 candidate별 owner, DESIGN_CONTRACT는 사용할 자원과 대표 화면 품질 기준, STATE_MATRIX는 실제 흐름, CRITIQUE는 전체/세부 관찰, EVIDENCE_MANIFEST는 candidate/revision과 출처·실행 증거를 가진다.

§13.7–13.10의 세부 기록도 이 일곱 산출물에 넣는다. 새 DB·별도 운영 대시보드·스킬별 중복 보고서는 요구하지 않는다. 작은 국소 수정에서는 영향을 받는 관계·자원·claim만 기록하되, material 재설계의 통합 관찰은 생략하지 않는다.

정적 concept, 실제 렌더, 실제 상호작용, 실제 데이터 연동을 서로 다른 증거 종류로 기록한다. 모든 후보를 보존하고 선택본만으로 최초 생성 성공률을 주장하지 않는다. 구현된 차단과 아직 설계에만 있는 차단은 명시적으로 구분한다.

현재 변경은 제작/검사 설계의 보완이다. 실제 화면 품질 향상과 허위 완료 감소는 동일 brief의 Control/Candidate 평가 전까지 미검증이다.

### 13.7 참조 선택과 합성의 실행 계약

참조의 인기도·업종 키워드·스타일 이름으로 선택하지 않는다. 먼저 이번 제품의 핵심 행동, 실제 콘텐츠 길이/밀도, 이미지 역할, 필요한 상태와 좁은 화면 제약을 DESIGN_INTENT에서 읽는다. 승인 원본이 있으면 보존할 관계를 먼저 고정한다.

검색 결과마다 `source_id`, 출처/접근 시점, 실제 열어 본 화면/viewport/state, 사용할 관계, 제품과의 차이, 필요한 자원, 제외 이유를 REFERENCE_CANDIDATES에 남긴다. 메타데이터만 읽은 후보는 VISUAL_UNINSPECTED다. 실제 관찰 없이 설명을 시각 근거로 바꾸지 않는다. 정적 화면에서 인터랙션 품질을 추정 확정하지 않는다.

후보 선정은 다음 순서로 한다.

1. 제품 의미·필수 정보·핵심 행동을 훼손하거나 실제 콘텐츠를 담지 못하는 후보는 제외한다. 대표 상태가 없으면 그 부분의 근거 부족을 표시한다.
2. 참조의 미감이 특정 사진/폰트/짧은 영문에 의존하는지 확인한다. 현재 자원으로 관계를 재현할 수 없는 후보는 자원 확보 가설을 검증하기 전 확정하지 않는다.
3. 남은 후보는 실제 콘텐츠를 넣었을 때의 위계·밀도·이미지 관계·모바일 재구성 차이를 비교한다. 합산 점수 대신 어떤 장점과 손실 때문에 선택하는지 적는다. 낮은 품질의 후보 중 1위도 자동 채택하지 않는다.
4. 선택한 참조에서 **보존할 관계 / 프로젝트에 맞게 변환할 관계 / 가져오지 않을 요소 / 변환의 실패 조건**을 정하고 candidate 계약으로 잠근다. 탐색 단계의 관계는 proposal이며 승인된 프로젝트 방향과 구분한다.
5. 실제 대표 화면으로 가설을 검증한다. 참조가 멋있다는 판단과 이번 제품의 결과가 좋다는 판단은 별개다. 실화면이 실패하면 구현 세부 또는 참조 가설 중 어디가 틀렸는지 구분해 되돌린다.

최소 합성 기록은 `observed_relation → product_constraint → transformation → expected_render → falsifier`다. 수치가 필요한 값은 실제 원본/렌더 측정이나 프로젝트 계약에서 가져오고, 추정이면 명시한다. 예시는 다음과 같으며 **실제로 조회한 참조나 검증 결과가 아닌 형식 예시**다.

| 관찰했다고 가정한 관계 | 제품 제약과 변환 가설 | 실제 렌더에서 반증할 조건 |
|---|---|---|
| 사진이 1차 시선, 제목은 사진 옆 짧은 문장 | 한글 제목이 길다면 사진/제목의 위계는 보존하고 컬럼 비율·줄바꿈은 실제 콘텐츠로 재조정 | 제목이 핵심 행동을 밀어내거나 이미지가 증거/정보를 가림 |
| 서로 가까운 수치가 비교 그룹으로 읽힘 | 단위·보조 설명·빈 값을 포함한 실제 데이터로 그룹 간격과 정렬을 설계 | 그룹 경계가 흐리거나 긴 값이 다른 그룹에 붙어 읽힘 |
| 좁은 화면에서 우선 행동 뒤 보조 정보가 이어짐 | 데스크톱 축소 대신 제품 우선순위에 따라 재배치 | 필수 정보 누락, 의미 순서 역전, 키보드 순서 불일치 |

OMD 경로의 실제 가용성·검색 schema·결과 품질은 현재 미검증이다. 구현 시 알려진 입력으로 검색→원본 열람→source ID 연결을 확인해야 한다. 검색 불가 시 승인된 원본이나 출처가 확인된 대체 자료로 진행한 사실을 기록할 수 있으나 OMD 조회 성공으로 보고하지 않는다. 대체 근거도 없으면 REFERENCE_LOCKED로 넘어가지 않는다. 새 corpus 구축은 이 문제의 기본 해법으로 삼지 않는다.

### 13.8 개별 축과 전체 화면의 통합 검수

단일 축 owner는 변경 책임을 명확히 하는 규칙이며 축들이 독립적이라는 가정이 아니다. Primary가 전체 구성을 책임지고 Secondary의 요소는 Primary 구도에서 실제로 어울리는지 검증한 뒤 채택한다. 서로 다른 후보의 좋은 부분을 섞으려면 새 candidate/계약 revision으로 합성하고 다시 관찰한다.

DESIGN_CONTRACT에 이번 화면에서 중요한 결합 관계만 남긴다. 예: 폰트 폭↔제목 줄수↔이미지 높이, 정보 밀도↔그룹 간격↔강조 색, sticky 영역↔포커스 가림, 모션↔읽기 순서, 모바일 순서↔핵심 행동. 모든 축 조합의 기계적 전수검사는 요구하지 않는다.

J가 통합 구성 검수 R, I가 C1, U가 C2이며 독립 최종 판정 A는 §5의 Critic이다. 결합 관계의 특정 접근성/동작 결함은 V/U 등 기존 owner가 계속 맡는다. 통합 검수에서 다음을 실제 조건으로 확인한다.

- 전체 페이지의 처음→중간→끝 흐름과 section/화면 사이의 리듬, 핵심 작업의 전후 상태.
- 확대 디테일과 전체 구도 양쪽에서 강조/밀도/정렬이 일관되는지.
- 실제 언어·이미지·긴 값·좁은 화면에서도 핵심 정보와 행동의 우선순위가 유지되는지.
- 모션이 있는 경우 정지 화면뿐 아니라 전환 중·완료·재입력과 reduced-motion에서 같은 의미가 유지되는지.

개별 type/image/spacing이 각각 PASS여도 통합 위계가 깨지면 Visual Quality는 FAIL이다. 합산 평균으로 상쇄하지 않는다. 국소 수정 후에는 관련 결합 관계와 보호 영역을 재검사한다. 최초 대표 화면과 최종 확장 결과에는 통합 검수를 반드시 수행한다.

### 13.9 이미지·폰트·콘텐츠 준비와 대체 경로

DESIGN_INTENT의 자원 항목에 역할, 사용 위치, 품질에 미치는 중요도, 원본/출처와 사용 근거, 현재 상태, 획득/대체 방법, 담당자, 검증 위치를 기록한다. 상태는 VERIFIED / PROVISIONAL / MISSING / REJECTED다. 내려받았거나 import에 성공한 것만으로 VERIFIED가 되지 않는다.

- 먼저 승인된 프로젝트 원본과 실제 제품 데이터를 확인한다. 부족하면 작업 권한 안에서 확보 가능한 자료를 찾거나 제작한다. 외부 결제·계정 권한 등 실제 종속 조건이 필요한 경우에만 해당 결정을 요청하고, 무관한 제작은 계속한다.
- J가 이미지의 역할·선정·크롭 R/A, I가 디테일 C1, U가 콘텐츠 적합성 C2다. 확보/연결의 실행 R은 구현자 또는 자원 제작자다. 제품의 사실·문구 변경 A는 기존 Product authority다. 스킬은 실제 asset 생산 도구를 대신하지 않는다.
- 후보 이미지는 원본 크기/품질, 화면별 초점과 크롭, 주변 텍스트와의 관계를 실제 렌더로 확인한다. 생성 이미지나 가상 데이터는 시각 탐색에 사용할 수 있으나 실제 고객·제품 결과·차트의 증거로 표시하지 않는다.
- 폰트는 지원 언어/한글 glyph, 실제 로딩된 family/weight, 줄바꿈과 fallback 발생을 확인한다. I가 표현 R, 구현자가 로딩 확인 R을 각각 맡는다. 지원하지 않는 굵기의 합성이나 의도하지 않은 fallback을 최종 타이포 검증으로 통과시키지 않는다.
- 콘텐츠는 짧은/긴/빈/오류 값 및 단위·날짜·다국어의 실제 분포를 포함한다. fixture면 출처와 한계를 명시한다. U가 상태·내구성을 확인하고 Product 의미는 바꾸지 않는다.
- 필요한 자원을 얻지 못하면 승인 방향 안에서 대체 가능성을 검증한다. 대체가 구도/의미/브랜드 약속을 바꾸면 계약 revision과 해당 authority 결정이 필요하다. 실제 품질을 좌우하는 자원이 PROVISIONAL/MISSING이면 관련 품질 gate는 UNVERIFIED다. 관찰된 결함이 있으면 FAIL을 함께 남긴다.

자원 준비는 후보 선택 전에 가능성을 확인하고, 최종 관찰 전에 실제 사용본으로 확정한다. 나중의 asset/font/content 교체는 변경이며 관련 렌더·계약 적합성·승인 범위를 무효화할 수 있다.

### 13.10 수정의 개선 판정과 수렴

수정 단위마다 CRITIQUE에 원인 가설, 변경할 관계, 기대 효과, 보호할 영역, 같은 조건의 before/after 증거, 실제 개선/회귀/미확인 결과를 남긴다. 미감 전부를 숫자로 바꾸지 않는다. 해당 결함이 사라졌는지, 위계가 의도대로 읽히는지처럼 관찰 가능한 기준으로 비교한다.

| 관찰 결과 | 다음 행동 | 품질/완료 상태 |
|---|---|---|
| 목표 결함 해소, 영향 범위 회귀 없음 | 변경 유지, 남은 필수 claim 진행 | 해당 claim만 갱신 |
| 개선 근거 불충분 또는 다른 문제로 이동 | 재관찰 또는 더 나은 이전 버전 보존/복구 | 기존 FAIL/UNVERIFIED 유지 |
| 같은 원인 국소 수리 2회 실패 | 작은 수정 누적을 중단하고 참조·자원·구도·계약 재진단 | REWORK |
| 재진단 후 실행 가능한 새 가설/자원 있음 | 가설이 바꾸는 축과 재검증 범위를 정해 진행 | 미해결 상태로 작업 계속 |
| 재진단 후 새 근거/실행 가능한 가설 없음 | 남은 결함, 시도, 필요한 입력/결정을 보고하고 해당 작업 중지 | unresolved; PASS 금지 |
| 필수 claim과 내부 품질 충족, 정확한 사용자 승인 대기 | 현재 패키지 제출 | USER_REVIEW; APPROVED 아님 |

2회는 동일 원인에 대한 접근 전환 신호이며 전체 작업의 품질 상한이나 미감 측정값이 아니다. 설명만 바꾼 동일 수정은 새 가설로 세지 않는다. 개선 없는 반복·서로 상쇄하는 왕복 수정도 재진단 대상으로 삼는다. 중지는 실행 처분이고 FAIL/UNVERIFIED는 결과 판정이므로 별도 필드로 유지한다.

필수 기준을 충족한 뒤의 선택적 polish는 남은 구체적 품질 기회와 부작용을 비교해 진행한다. ADVISORY 제안이 더 있다는 이유만으로 영구 미완료로 만들지 않는다. 반대로 추가 시간/예산이 없거나 아이디어가 고갈됐다는 이유로 남은 필수 결함을 면제하지 않는다. 사용자에게 올릴 것은 추상적 '더 할까요'가 아니라 실제 전후 화면, 미해결 문제와 필요한 결정이다.

## 14. 상태·gate·증거의 일관성

작업 단계(stage), claim verdict, 실행 처분, 사용자 승인 범위를 분리한다. IMPLEMENTED/CRAFTED는 해당 활동이 수행되었다는 뜻이고 품질 PASS가 아니다. 모든 상태는 `candidate_id + revision + scope`에 귀속한다.

| 상태/전이 | 요구 조건과 한계 |
|---|---|
| INTENT_READY → REFERENCES_FOUND | 필수 제품 의미/범위 확인; 실제 열람한 참조와 출처 존재. 자원 미확인은 명시 |
| REFERENCES_FOUND → REFERENCE_LOCKED | Primary/Secondary와 축 owner, 관계 변환·제외 근거 확보. 최종 사용자 승인이 아닌 후보 계약 가능 |
| REFERENCE_LOCKED → CONTRACT_READY | 적용 규칙, 품질 기준, 대표 화면, required states, 사용할 자원/한계, 영향 범위 명시 |
| CONTRACT_READY → IMPLEMENTED → CRAFTED | 해당 revision의 실행 결과와 craft 작업 기록. 탐색 fixture 가능하나 최종 품질과 구분 |
| CRAFTED → PROOF_COMPLETE | required matrix의 모든 필수 관찰을 현재 revision으로 수행하고 신뢰 조건 충족. 관찰된 FAIL은 숨기지 않으며 proof 완비와 통과를 구분 |
| PROOF_COMPLETE → CRITIC_REVIEWED | 실제 독립 검수와 scope/calibration 기록 존재. reviewed 자체는 PASS가 아님 |
| 임의의 작업 단계 → USER_REVIEW | 현재 화면·gate·누락·한계를 표시하여 피드백/결정 요청 가능. stage 진행과 별도 검토 event로 기록하여 앞 단계를 완료한 것처럼 표시하지 않음 |
| USER_REVIEW → APPROVED | exact 사용자 승인 + 현재 scope의 필수 gate 전부 PASS + 미해결 필수 finding 없음. 일부만 승인되면 그 scope만 해당 |
| 변경/실패 → REWORK | 관련 계약·코드·자원 revision 갱신과 영향받은 증거/판정/승인의 무효화; 재진입은 실패 원인에 해당하는 단계 |

전이 계산은 §10.2–10.4의 validator가 담당한다. 미실행 검사, 도구 실패, calibration 부족을 단계 이름으로 숨기지 않는다. UNVERIFIED라도 사용자가 화면을 좋아하거나 방향을 선택할 수 있지만, 이는 User Acceptance/방향 선택 기록이며 기술·내부 품질 인증을 대체하지 않는다. 사용자 승인 후에도 Harness의 품질 향상 효과는 별도 실험 전까지 미검증이다.

## 15. 이번 개정과 남은 검증

| 이전 빈틈 | r2 변경 | 아직 필요한 실제 검증 |
|---|---|---|
| 참조 선택/번역이 추상적 | §13.7 제외 조건·관계 변환·실화면 반증 | OMD retrieval와 실제 brief 합성 |
| 축별 합격으로 전체 조화 추정 | §13.8 결합 관계·전체 흐름 관찰 | 실제 화면에서 통합 결함 검출 |
| 독립 Critic을 신뢰 가능한 미감 판정으로 간주할 위험 | §10.3 보정/보류 자료·cold start·판정 제한 | 실제 사용자 평가와 누락/오판 기록 |
| 자원 미준비의 해결 경로 부족 | §13.9 확보·검증·대체·재검수 | 실제 폰트/이미지/콘텐츠 로딩과 렌더 |
| 자기 작성 증거로 완료를 위조할 가능성 | §10.4 신뢰 등급·호스트 receipt·validator 경계 | 호스트 capability 확인과 위조 주입 테스트 |

| 최초 제출본으로 초기 실패를 숨길 위험 | §12 및 조사 보고서 §11의 3시점 기록 | 전체 run 보존과 사용자 블라인드 비교 |

구현된 일곱 산출물과 CLI의 정책 분기는 합성 테스트로 검증되었다. 시각 제작 보완과 모션 검증 gate의 회귀 테스트도 통과했다. 실제 호스트 receipt 연동, 디자인 품질 개선 및 사용자 만족은 검증되지 않았다. 두 제한된 A/B에서도 추가 관계 진단 규칙의 고유 효과가 확인되지 않아 기존 설치판을 유지한다. 문서·schema·테스트 통과를 완성된 디자인 제품으로 부르지 않는다.
